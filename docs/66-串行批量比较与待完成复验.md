# 串行批量比较与待完成复验

2026-10-16用户要求测不同请求路线数的间隔，最终得到串行调用最佳策略。本次完成基础比较，但更快档位的最终复验因真实日配额用尽未执行；不能将本轮写成全局最优策略已完成。

## 真实调用方式

腾讯云同一服务端AK、同一公开王府井中心、百度步行矩阵接口直连。所有请求串行在途，按发出时刻控制起始间隔，排除已有有效OD缓存，无网络或业务隐式重试。每档目标18批；401后停止该档、65秒冷却、间隔增加0.5秒再验证。各组样本数相同而持续时长不同，不能把短样本当作长期容量证明。

工具`tools/demo/benchmark_matrix_envelope.py`新增pairs-per-request、fixed-interval、confirmation-requests、interval-step及output-name参数。固定批量模式显式使用--run-live。组间至少保留最近探测响应后10秒的间隔，避免两个进程交接时额外突发；不会清空账号侧更长窗口。各阶段并非与其他账号调用完全隔离的实验。

每次请求写产品账本，成功原始响应写正常API缓存；不写研究账本，不清库，不改线上环境或限流。

## 可用的串行策略结论

在已完成的候选档中，50对/9秒、40对/7.2秒、10对/1.8秒均折算约5.56对/秒；20对/4.1秒约4.88对/秒，30对/6秒为5对/秒。不同样本时长和前序账号负载使这些观测不能直接证明全局固定线性上限，20对/3.6秒失败尤其不能忽略。

对独立且已全部就绪的大批量OD，优先合并至每次最多50对，采用当前已验证的9秒起始节奏，在上述相同名义吞吐的方案中可减少HTTP请求数量（1000对约20次，相比40对约25次、10对约100次）。例如149对拆50+50+49，按已测起始节奏估算最后一批在18秒发出，加响应约0.1秒；这是调度推算，不是本轮重新测得的完整149点任务。

对二分算法下一轮才产生的探针，不应等待凑满50对，也不能每个小批次固定等9秒。应按实际批量节奏调度；本次直接验证的是表中明确列出的批量和间隔，其他批量的插值仅是设计建议，需要后续验证。全局共享一个OD发送队列，串行在途1，缓存命中不占路线发送预算，401和302分开处理。

上面的50对/9秒是当前已测候选中的参考选择，不是所有批量、所有间隔和长时运行的全局最优或稳定权益。生产要留余量，且不能将没有通过20对/3.6秒这一事实藏掉。

## 未完成与停止条件

原计划在基础比较后，对40对从6.4秒开始连续36批提速复验，401后按0.5秒放慢。启动器先检查上一组完成状态，发现302对应的stopped后退出，因此没有发出该组任何请求。

收到302后停止所有真实探测，未为了补结果更换AK、取消限制或继续重试。需要接口日配额恢复或调整后才能完成提速复验；本轮没有验证确切重置时间或额度数值，也未自动创建后续定时任务。
