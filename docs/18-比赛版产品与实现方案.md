## 1. 产品与版本决策

比赛版采用“百度真实空间数据 + 模拟行为耗时 + 真实规划计算”。主体验：用百度API取得公司→家路线和沿途POI，查看选中POI基于真实步行测时生成的等时圈，将POI与其他待办一起规划，控制回家时间。补充「时间空档」与「社区体检」，历史案例说明研究基础。

数据原则：百度能够提供的地址、坐标、POI、导航引导点、营业时间、路线、距离和路径耗时不模拟；API不提供或缺失的排队、购物/办事停留、用户偏好和临时事件可以模拟并逐字段标注。比赛版只使用真实百度 API；服务端缓存只保存真实响应，用于去重、限流和减少重复调用，不作为独立离线模式。最终按赛事原文核对交付要求。

## 4. 沿途POI功能设计（核心新增）

### 用户流程

1. 输入公司和家，由百度地理编码/地点检索确认位置；步行路线API返回基准路线与路径耗时。
2. 选择超市/药店/咖啡/快递等类别。系统沿路线分段搜索百度POI、翻页并按UID去重；用户设置“最多额外走10分钟”和模拟停留时长。
3. 路线矩阵计算每个候选的实际绕行，候选卡展示额外路程时间、模拟办事/等待、预计到家、余量和API返回的营业时间（缺失显示未知）。
4. 点一个POI后才按需计算并缓存5/10/15分钟等时圈，显示基准路线、推荐离开路线点、返回点和绕行支路，避免为所有候选批量烧配额。
5. 可切换「保留通勤路线」与「允许整体换路」，说明两者对到家时间的影响。
6. 点击「加入今天安排」后固定这家店；也可选择「同类任选」交给全局规划器比较。
7. 再加入其他任务，整体重算顺序和路线；执行中关闭门店/桥梁后重排。

界面默认仅展开一个POI的圈，最多比较3个POI，控制图层杂乱。路线段与选中POI颜色一致，去程/出发圈用图例区分；图层开关不改变计算结果。

### 计算口径

令T(a,b)为百度步行路线矩阵返回的有方向耗时。公司S、家H、基准路线几何R=(r0…rn)和B=T(S,H)来自步行路线API。默认展示p的出发等时圈I_out(p,b)={x:T(p,x)<=b}；寻找路线上能去p的接入点时，批量测量I_in(p,b)={x:T(x,p)<=b}。两者不假设对称。

沿途判定分三步：沿R若干采样中心进行周边POI检索，仅作召回→用路线矩阵测S→p和p→H得到真实绕行→选中POI后，用路线采样点↔p矩阵及POI等时圈解释接入/返回。POI距路线近、圈相交都不是最终可行性结论。

自由重规划：额外路程时间Δ=T(S,p)+T(p,H)−B。

保留路线：对有序接入/返回节点i<=j求最小值：

`T_R(S,ri) + T(ri,p) + T(p,rj) + T_R(rj,H) − B`

T_R由基准路线步骤累计；r_i/r_j取路线按距离抽样的百度坐标，T(r_i,p)、T(p,r_j)由路线矩阵实测。接入和返回不要求同一点。为控制配额，先对候选POI和稀疏路线样本批量测量，再对选中POI细化；P0不处理连续道路上任意切入点。

POI圈由现有射线二分/自适应加密算法调用百度步行矩阵生成，缓存键含POI UID/坐标、阈值、算法版本和百度响应hash。POI圈预算、额外绕行预算是独立参数。所有合法i/j保留供时间窗判断；若API营业时间存在则校验，缺失显示未知，并允许用户确认或使用有来源标记的演示时段。

总额外耗时=Δ+等待+服务；最终到家需<=deadline。相同POI、数据、事件下两种模式的差别必须来自上述计算。多POI加入后调用全局规划，不能简单相加独立Δ（共享路段会重复计费）。P0多任务采用自由整体规划，若用户在保留路线模式中选点，加入前明确提示多任务将整体重排；多站固定路线约束不默默假装已支持。

### 必须能演示的反例

- 河对岸商店直线很近，绕桥成本高，被实际绕行预算排除。
- 百度返回的去/回耗时不对称，不能用一个圈代替两个方向。

## 6. 数据来源、缓存与契约

### 数据分层

| 数据 | 首选来源 | 缺失处理 |
|---|---|---|
| 公司/家位置 | 百度地理编码、地点检索、用户确认 | 无结果时要求重选，不生成假坐标 |
| POI名称/UID/坐标/导航点/分类 | 百度Place搜索和详情 | 扩展taxonomy、走廊分段搜索、翻页；仍缺失则不声称存在 |
| 营业时间 | `shop_hours`及可用结构化时段 | 显示未知；演示需要时允许单字段模拟并标注 |
| 营业状态 | 百度高级权限返回值 | 未返回就是未知，不推断正在营业 |
| 基准/绕行路线、距离、耗时、几何 | 百度步行路线/路线矩阵 | 失败走API缓存；均无则该方案不可用 |
| POI等时圈测值 | 百度步行矩阵 + 本项目采样重建 | 配额不足返回降级状态，不写假半径 |
| 店内停留、排队、用户偏好 | 用户输入或固定seed模拟 | 明示“模拟假设”，可编辑 |
| 临时关店、延误、断路 | 演示事件 | 明示情景模拟，不称实时事件 |

live模式经服务端访问百度。沿基准路线按重叠圆形窗口搜索多关键词，直到空页或API总数边界，按UID去重；记录query、窗口、页码和响应hash。由于API数据本身可能滞后/截断，UI显示召回方法与“百度可检索数据”限制。

服务端缓存保存脱敏的真实百度响应、请求参数摘要、坐标系、时间和hash；禁止手工创建“像百度返回”的POI或路线。敏感参数与密钥不落盘。历史案例另导出到cases，所有原始SQLite只读。

live 地图使用百度 JSAPI 4.0 底图并封装项目地图适配层；JSAPI 负责底图、点选及覆盖物，业务路线/POI/等时圈仍通过本项目后端真实 API 与缓存计算。所有几何显式记录 CRS，百度地图默认 BD09，导出标准 GeoJSON 前转换为 WGS84。SDK/业务 API 不可用时分别报错，不生成假路线或假 POI。

## 7. 共用规划算法

先用百度路线矩阵为公司、家和候选POI构建有方向OD表，再枚举任务顺序和候选。每类最多3个、任务最多5个，用先后依赖、营业/任务窗口和deadline剪枝；朴素完整组合上界120×243=29,160。规划器用小型合成OD穷举oracle验证，业务场景的OD必须来自API/live缓存。

早到可等开门，服务完成<=关门。全部路程、等待、服务及返程计入最终时间。最快目标最小完成时间；最少步行目标最小步行距离，以完成时间破平。P0纯步行下两者可能相同，方案去重，绝不凑数。

无解返回原因及放宽建议，用户接受后才能跳过必须任务。执行事件在路网节点发生，保留已完成部分；不模拟连续GPS。缓存key含dataset/event/方向/阈值/目标，事件后重算受影响数据。

时间空档判断：API的T(start,p)+模拟/用户等待+模拟/用户服务+API的T(p,return)<=预算，并在已知营业时间下校验；不同起终点和方向均支持。范围图由实测候选或测时场产生，不能用单程欧氏圆替代。

## 8. 社区体检与原实验的关系

中心等时圈继续复用百度步行测时算法，用于「中心能去哪」。居民采样点到百度可检索设施的步行矩阵用于「样本点可否获得服务」，两种口径不混用。无人口数据只称采样格网覆盖；POI召回不完整时显示数据完整度限制。

五类演示权重医疗.25/教育.20/购物.20/药店.15/养老.20，明确非官方标准。新增服务点位置是假设情景，前后同一格网、阈值和权重重新计算；既有设施和基础通行时间仍来自百度API。历史案例展示黑盒测量与重建证据。

原始步行缓存多为中心到目的地，不能作为完整任意OD。历史指标按对应脚本标记分类IoU/其他口径，不擅称几何面积IoU；新模拟规划不能引用历史0.935等数值宣称本功能精度。

## 9. 场景与演示

| ID | 场景输入/事件 | 必须观察到的性质 |
|---|---|---|
| S00 沿途挑店 | 真实百度公司/家/药店，切换POI圈阈值与绕行预算 | 显示API路线/POI/等时圈、模拟停留、实际预计回家时间 |

| S02 时间空档 | 接人前40分钟，返回指定节点 | 单程可达但往返办不完的点被排除 |
| S03 临时关店 | S01完成首任务后注入模拟关店 | 已完成锁定，替换未访门店，标明情景模拟 |
| S04 路线延误 | 对未完成路线注入模拟延误/不可用 | API基础路线保留来源，情景派生结果同步重算 |
| S05 时间不足 | 缩短deadline/延长服务 | 无解解释，接受放宽后恢复 |
| S06 社区改善 | 添加一个养老服务点 | 覆盖率、盲区、分数真实联动，可还原 |

S00—S02及S06在联网环境直接调用真实 API；重复请求可命中真实响应缓存。模拟字段单独生成且可编辑。每场景含请求摘要、API缓存版本、假设、事件、reset和预期性质。3分钟讲稿：沿途选店45秒→加入任务45秒→关店重排35秒→空档20秒→体检20秒→历史证据15秒。
