# 步行矩阵单批五十对与连续发送实测

2026-10-16用户要求“别墨迹，一次测到底，到底一次能多少对不触发限流”。官网核实步行批量算路单次起点数×终点数最多50条，因此直接测试合法最大批量，不重复逐档小批探测，也不发送超过50条的无效参数。

官方来源：https://lbsyun.baidu.com/docs/webapi?title=routematrix/routchtout 。官方同时说明配额与并发按最终路线数计算，而不是只按HTTP请求次数。

## 结果

在腾讯云服务器使用原服务端AK，正式BaiduAdapter直连；每请求1起点×50个未命中缓存的终点，无自动重试。成功响应写入原API缓存，各次尝试写入产品账本，未改变线上服务参数或冷却逻辑。

| 档位 | 相对发出时间 | 路线数 | 有效数 | 状态 | 网络响应 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 间隔6.2秒 | 0秒 | 50 | 50 | 0 | 118ms |
| 间隔6.2秒 | 6.2秒 | 50 | 50 | 0 | 121ms |
| 间隔6.2秒 | 12.4秒 | 50 | 0 | 401 | 79ms |
| 间隔18秒 | 0秒 | 50 | 50 | 0 | 158ms |
| 间隔18秒 | 18秒 | 50 | 50 | 0 | 113ms |
| 间隔18秒 | 36秒 | 50 | 50 | 0 | 180ms |

首档收到401后立即停止，没有在冷却期间重试。第二档实际开始时间为02:12:08.061709 UTC，距上一档401返回约50秒；代码要求至少间隔16秒，实际间隔包含准备和排查时间。

结论：单请求50对已经实测成功，也是该步行接口单批合法上限。连续每6.2秒发50对会在本次第三批触发401；每18秒发50对本次连续3批全部通过。不把单批50对成功理解成50对/秒，也不把18秒称为精确最小间隔或长期稳定容量。未进一步二分发送间隔或追加压测。

合计6次HTTP尝试、300对成本、250对有效、1次401。6.2秒档从第一批至结束12.487秒，18秒档36.195秒，其中包含主动安排的间隔，不能当作纯算法或网络耗时。
