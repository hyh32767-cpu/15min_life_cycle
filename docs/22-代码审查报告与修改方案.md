## 二、主要审查问题

### F1：前后端规划请求契约不一致

严重级别：高  
类型：接口契约 / 功能阻断

前端规划请求发送 `label`、`placeName`、`coord`、`opensSeconds`、`closesSeconds`；后端 `PlanTaskRequest`、`PlanOptionRequest` 使用 `extra="forbid"`，并没有这些字段；营业时间还要求嵌套在 `window` 中。

重规划请求额外发送 `startId`、`departureSeconds`，但 `ReplanRequest` 也没有定义。

相关文件：

- `web/src/stores/plan.ts:230`
- `web/src/stores/execution.ts:128`
- `api/app/models/api.py:106`
- `api/app/models/api.py:220`

已用 Pydantic 复现，前端 payload 会触发 `extra_forbidden`，因此规划和重规划接口无法正常工作。

修改方案：

- 将前端展示对象和 API DTO 分离。
- 规划接口只发送后端真正需要的字段。
- 营业时间改为 `window.opensSeconds` / `window.closesSeconds`。
- 重规划请求删除后端不需要的 `startId`、`departureSeconds`，或统一扩展后端模型。
- 增加一条真实前后端 API 集成测试。

### F2：`required=False` 没有实际效果

严重级别：高  
类型：算法正确性

`TaskSpec.required` 字段存在，但 `plan_tasks()` 始终枚举所有任务，没有选择性跳过可选任务。

相关文件：

- `core/planner.py:39`
- `core/planner.py:241`

影响：

- 用户取消“必须完成”后，任务仍然参与规划。
- 可选任务可能导致整个方案被判定为无解。
- UI 上的“必须完成”复选框目前是无效功能。

修改方案：

- 必做任务始终加入规划。
- 可选任务枚举子集，并在目标函数中优先选择更多可选任务，再优化时间/步行。
- 明确前置关系：可选任务被跳过时，其后继任务也跳过，或自动将前置任务提升为必选。
- 增加 required/optional 单元测试和 API 验收测试。

### F3：关闭必做任务后会被静默删除

严重级别：高  
类型：重规划逻辑

`_filter_closed()` 在任务无可用 POI 时直接丢弃任务，没有检查 `required`。

相关文件：

- `core/replan.py:45`

修改方案：

- required 任务无可用候选时返回 `REQUIRED_TASK_CLOSED`。
- optional 任务才允许被移除。
- 结果中记录被跳过任务和不可行原因。

### F4：首次重规划从起点 S 开始

严重级别：高  
类型：执行状态错误

首次重规划时 `replan.value` 为空，当前位置退回 `S`，而不是用户刚完成任务的 POI。

相关文件：

- `web/src/stores/execution.ts:121`

修改方案：

- 在执行状态中持久化 `currentNodeId`、`currentTimeSeconds`、`completedTaskIds`。
- 用户完成任务后立即更新 `currentNodeId`。
- 重规划直接使用执行状态，不从旧方案反推当前位置。
- 增加“完成第一个任务后重规划”的 E2E 测试。

### F5：百度矩阵请求可能超过 50 对限制

严重级别：高  
类型：API 配额 / 性能

5 个任务、每个 3 个候选时，节点数最多为 17 个，完整矩阵为 289 对；当前前端一次发送完整矩阵，后端也只调用一次百度接口。

相关文件：

- `web/src/stores/plan.ts:166`
- `api/app/services/baidu_service.py:477`

修改方案：

- 在后端按最多 50 对拆分请求。
- 合并所有批次的 cell。
- 保留每个批次的 `traceId`、`requestHash`、`responseHash`。
- 对缺失 cell 显式补充 `no_route` 或 `error`。
- 增加 17×17 矩阵集成测试。

### F6：Docker 默认 replay 与前端模式不一致

严重级别：高

### F8：等时圈缓存 key 不完整，失败结果会永久缓存

## 六、第二轮复审补充

### F13（部分修复）：replay 缺失路线时仍可能被近似坐标 alias 到 S00 路线

严重级别：高  
类型：数据完整性 / replay 正确性

当前 `ReplayProvider.getWalkingRoute()` 已限制只有接近登记 S00 公司/家庭坐标的请求才允许 alias；任意远处坐标会正确失败。但 alias 判断仍使用经纬度各自 0.005 的宽松范围，范围内不同地点可能被映射到同一条 S00 基准路线，仍不是严格的请求级 fixture 命中。

相关文件：

- `web/src/providers/replay.ts:443`
- `web/src/stores/commute.ts:181`

另外，通勤页的 fallback 没有限制为 replay 模式，live 模式出现 `NO_ROUTE` 时也可能静默改用 POI 中心点重试。

修改方案：

- replay 只允许对明确登记的坐标别名做 fallback。
- 未录制的请求必须失败并显示 fixture 缺失。
- live 模式禁止使用 replay fallback；导航入口失败应保留真实错误。
- 增加“任意未录制坐标必须失败”的测试。

### F14（批量拆分已修复，缺失数据策略仍不合规）：replay 矩阵曾没有批量拆分

严重级别：高  
类型：演示可用性 / 算法一致性

前端现在已经按 ≤50 对拆分并填充完整网格，但缺 fixture 时改成了直线速度模拟，详见第三轮 F29。当前 replay 数据仍没有覆盖真实多节点 API matrix，手动添加 POI 会进入模拟 OD，而不是明确失败。

相关文件：

- `web/src/providers/replay.ts:472`
- `web/src/stores/plan.ts:188`
- `demo-data/v1/manifest.json`

修改方案：

- replay provider 与 live provider 使用相同的 ≤50 对拆分策略。
- 录制规划所需的多节点矩阵 fixture，或在 replay 中对已录制 OD 做明确的本地模拟并标注来源。
- 增加 1×1、2×2、17×17 replay 测试。

### F15（最少步行/来源已部分修复，时间窗 parity 残余）：replay 本地规划曾没有实现“最少步行”目标

严重级别：中高  
类型：live/replay 算法不一致

当前 `planLocally()` 已读取 `preference`、`distanceM` 和延误来源，最少步行排序的首要问题已修复；但它仍只处理单个 `window`，多窗口/跨午夜和时间线 parity 问题见 F28。

相关文件：

- `web/src/providers/replay.ts:65`
- `web/src/providers/replay.ts:121`
- `web/src/providers/replay.ts:193`

修改方案：

- 复用 `core.planner` 的算法，或完整实现相同的 least-walk 排序。
- 在本地 lookup 中同时保存 duration、distance、sourceKind。
- 让 route delay 后的 cell 来源透传到 `PlanStop.travelSourceKind`。
- 增加 live/replay 同输入同结果的 parity 测试。

### F16（候选选择已修复，执行顺序残余）：执行完成任务时曾使用任务第一个候选

严重级别：高  
类型：执行状态错误

`completeTask()` 取 `task.options[0]` 作为当前位置，但整体规划可能选择同类任选任务的第二或第三个候选。之后重规划会从错误 POI 出发；`reopenTask()` 也有相同问题。

相关文件：

- `web/src/stores/execution.ts:60`
- `web/src/stores/execution.ts:80`

修改方案：

- 从当前选中的 `baseAlternative.stops` 按 `taskId` 找到实际 `placeId`。
- 以该 stop 的 `finishSeconds` 更新当前位置和虚拟时间。
- 若用户试图跳过前置任务，给出明确提示或要求确认。
- 增加多候选任务执行测试。

### F17（已修复）：复位按钮曾调用 setup store 的 `$reset()`

严重级别：高  
类型：前端运行时错误

`commute` 和 `plan` 是 Pinia setup store，Pinia 默认不实现 `$reset()`。点击“复位”会抛出：

```text
Store "commute" is built using the setup syntax and does not implement $reset().
```

相关文件：

- `web/src/stores/persistence.ts:83`

修改方案：

- 在各 setup store 内实现显式 `resetState()`。
- `resetAppState()` 调用三个 store 的显式 reset 方法。
- 复位后同时清理 localStorage、路由结果、执行事件和当前方案。
- 增加点击“复位”的 UI 测试。

### F18（部分修复）：本地持久化曾没有保存序列号和可恢复的执行结果

严重级别：中高  
类型：状态恢复

当前快照只保存任务和事件，不保存 `taskSeq`、`eventSeq`、规划结果、OD、当前位置和模式。

影响：

- 刷新后新增任务可能重新生成 `task-1`，与旧任务 ID 冲突。
- 新增事件可能重新生成 `ev-1`，造成重复 key。
- 刷新后执行页没有可用的规划结果，需要重新规划。
- 城市和 live/replay 模式也不会恢复。

相关文件：

- `web/src/stores/persistence.ts:15`
- `web/src/stores/plan.ts:24`
- `web/src/stores/execution.ts:16`

修改方案：

- 持久化并恢复 ID 序列，或从已有 ID 计算下一个序号。
- 保存 `result`、`travelTimes`、`nodeCoords`、`currentNodeId`、`currentTimeSeconds` 和模式。
- 对快照增加 schema version migration。

### F54：批量等时圈预算耗尽被记成 failed 而不是 skipped，状态语义与单射线实现不一致

严重级别：中  
类型：算法状态/配额可观测性

`core/isochrone.py:216-225` 在 `used_pairs + len(points) > max_pairs` 时返回全量 `None`，只添加 `probe_budget_exhausted`，不增加 `used_pairs`。随后 `:227-240`、`:253-274`、`:275-302` 把这些点全部加入 `failed_bearings`；`skipped_bearings` 在批量实现中从未填充。直接复现 `bearings=[0,45,90,135]`：`max_pairs=1` 得到 `status=failed`、`pairsUsed=0`、四个 `failedBearings`、空 `skippedBearings`；`max_pairs=4` 得到 `pairsUsed=4` 后剩余测量仍全部记 failed。

这会把“预算主动截断、没有发起测量”的射线伪装成“百度测量失败”，前端无法区分配额不足与上游错误，也与 `compute_isochrone()` 已有的 `skipped_bearings` 语义不一致。当前单测只断言“不造半径”，没有覆盖 skipped 分类。

修改方案：

- 在批量函数每次发现预算不足时，把尚未请求的 bearing 记录到 `skipped_bearings`，不要进入 `failed_bearings`；已成功取得的半径保留为 `partial`。
- `pairs_used` 应只统计实际发出的点；预算不足的剩余点不应生成 `ray_failed:*:measurement_missing` 警告，可单独增加 `probe_budget_exhausted:<n>`。
- 增加 `max_pairs=1/4` 的断言：`skippedBearings` 非空、`failedBearings` 不包含未测 bearing、无半径伪造，并验证 API 响应序列化保持该语义。

### 16.2 当前仍需处理的问题

#### F60：网络异常分支曾引用未定义的 `_RETRYABLE`（已在本轮修复）

`core/baidu_client.py` 的 live 请求异常处理原先捕获未定义名称 `_RETRYABLE`。一旦真实百度请求出现超时、DNS 或连接错误，异常处理本身会触发 `NameError`，无法返回统一的 `UPSTREAM_ERROR`。本轮补充网络异常集合，并把 `HTTPError` 放在网络重试分支之前，避免把百度已返回的 4xx/5xx 当作网络重试。

#### F61：浏览器 WGS84 自定位没有在百度请求唯一出口转换

`IsochronePage.vue` 将浏览器定位标为 `WGS84`，但 `BaiduService.walking_route/travel_matrix/isochrone_pois` 直接把 `Coord.lng/lat` 作为 BD09 请求参数，缓存 key 也固定写 BD09。当前没有业务层调用 `core.coord.wgs84_to_bd09` / `gcj02_to_bd09`。结果是自定位可能偏移数百米，并把错误坐标写入 API 缓存。

修改方案：在服务层建立唯一 `to_baidu_bd09(Coord)` 边界，先转换再构造请求参数和缓存 key；响应保留原始坐标与 `convertedFrom` 追踪字段；补 WGS84/GCJ02/BD09 三组契约测试。转换完成前，页面应明确提示“自定位暂不可用”或阻止提交，不能默认为 BD09。

#### F62：独立等时圈初始状态无法真正点选空白地图

`RouteMap.vue` 只有在已有 geometry、marker 或 isochrone 产生 `bounds` 时才渲染 SVG；`/isochrone` 初始状态没有任何图层，因此页面虽然提示“点击地图空白处”，实际没有可点击地图。当前 `T110` 又明确不接百度底图，不能把 SVG 示意误称为可定位地图。

修改方案：二选一并在 UI 诚实呈现：接入有中心/缩放/点击事件的百度底图适配；或把点选降级为“已有起点范围内的示意图点击”，首次起点只允许搜索/自定位，并移除“空白地图点选”的承诺。若保留独立点选 P0，优先实现前者。

#### F63：`setOrigin()` 未使旧等时圈/POI 请求失效（本轮已修复）

`web/src/stores/isochrone.ts` 原先的 `setOrigin()` 会清空结果但不递增 `seq` 和 `poiSeq`。本轮已在起点变更时递增两个序号并清理 loading/POI 状态，旧响应不会再写入新起点；仍应补一条“搜索/定位后快速换起点”的回归测试。

修改方案：保留当前序号失效逻辑，并把快速换起点、阈值切换和 POI 查询竞态纳入测试；必要时补 AbortController 取消网络请求以减少无效配额消耗。

#### F64：计划与执行 store 的 reset/replan 仍有 live 异步回写窗口（主要入口已修复）

本轮已让 `plan.ts.resetState()` 递增 `planGeneration`，并为 `execution.ts.runReplan/resetExecution()` 增加 `replanGeneration` 校验；复位或连续重排的旧结果不会覆盖当前状态。`fetchLegGeometries()` 等辅助请求仍没有同级 generation guard，需要补测试或统一请求生命周期。

修改方案：所有会清空/替换状态的入口递增 generation；每个请求捕获 generation 并在 success/error/finally 三处校验；增加“开始请求→复位→旧响应返回”和“连续两次重排”测试。

#### F65：API 缓存命中仍返回 `live-api`，等时圈来源被硬编码（已部分修复）

`BaiduService._resolve()` 原先在缓存命中时透传缓存记录写入时的 `source_kind`（通常为 `live-api`），导致缓存命中后的地点、路线和矩阵继续显示实时 API；本轮已改为返回 `api-cache`，并同步修正 `peek_matrix`。`IsochroneService.run()` 仍需完整聚合探针来源，当前只对全缓存和明显混合情形做了标记，无法覆盖“矩阵批次内部分命中”的所有组合。纯 live 不等于可以隐藏缓存命中。

修改方案：继续按 cell/探针聚合 `live-api`、`api-cache`、`derived`，多种来源显示“混合来源”；可增加 `fetchedSourceKind=live-api`/响应 hash 供追溯；账本继续区分 live request 与 cache hit。相应修改 API/前端契约测试。

#### F66：派生缓存命中生成的新 taskId 不可报告重取

`IsochroneService.run()` 在 `peek_cached` 命中时复制结果并生成新的 taskId，但没有把这个 taskId 持久化到 `DerivedCache`。随后 `GET /api/isochrones/{task_id}/report` 只能扫描已存结果，返回 404；`get_by_task()` 还只扫描最近 200 条记录。报告/导出链路因此不稳定。

修改方案：缓存命中返回已持久化 taskId；或增加 task→derived_key 索引表并在命中时登记别名；报告查询按索引读取，不设任意 200 条上限。

#### F67：等时圈报告统计与圈内 POI 截断语义不完整

`_isochrone_report()` 对偶数条半径取上中位数而非两中位数平均；`isochrone_pois()` 在 `max_unique` 后静默截断，没有向响应/页面暴露 `truncated` 和原因。用户可能把“百度可检索且受上限截断的 POI”误解为区域全量。

修改方案：修正偶数样本 median；返回并展示 `retrieval.truncated/truncationReason`、已检索页数和配额/分页限制，文案统一为“百度可检索 POI”。

### 17.2 新增与复核发现

#### F68：后端契约测试隐式依赖真实 AK，公共 CI 会失败并可能消耗配额（high）

`api/tests/contract/test_isochrones_api.py:71-117` 和 `test_closeout_api.py:137-173` 直接使用生产依赖，没有像其它路由契约测试那样 override `get_baidu_service`/`get_isochrone_service`。`Settings.from_env()` 在没有 `BAIDU_MAP_AK` 时 fail-closed，因此干净 CI 的静态案例、账本和等时圈测试会得到 503；若 CI 注入真实 AK，又会把测试变成不可复现的百度网络/配额调用。

修改方案：契约/单元测试统一使用 FakeAdapter、临时 cache/ledger/derived DB 和依赖 override；单独新增显式 opt-in 的 `api-live` smoke job，只有该 job 注入 AK 并计入真实调用账本。CI 的默认 `make api-test` 必须在无密钥、无网络条件下通过；测试名称和文档明确区分 contract 与 live smoke。

#### F69：百度 401 限流退避代码没有覆盖实际响应路径（high）

`api/app/services/baidu_service.py:80-95` 只捕获 `invoke()` 抛出的 `ServiceError`，但 `BaiduAdapter`/`core.baidu_client` 对百度 401 返回 `ApiResult(status=401)`，真正的 `ServiceError("RATE_LIMITED")` 在 `:113-114` 才抛出，已经错过重试分支。用 fake adapter 返回一次 401 再返回成功时，实际调用次数为 1 且直接抛 `RATE_LIMITED`，与注释声称的 3 秒/10 秒两次退避不符。

修改方案：在统一出口按 `raw.status == 401` 做有界退避，或让 adapter 把 401 映射为可重试异常；明确每次尝试的账本行/请求数语义，补 401→成功、连续 401、缓存命中不退避、超时不重复计费四组测试。退避不应阻塞 Web 请求线程，可在后续改为异步或短上限策略。

#### F70：等时圈“全 API 缓存但派生缓存缺失”时写入错误 key，导致派生结果永远无法命中（medium）

`api/app/services/isochrone_service.py:123-164` 的全缓存预检使用 `peek_hashes` 查派生 key；但预检命中且派生缓存未命中时，后续 `:152-165` 用空的 `upstream_hashes` 重新生成并写入 key。下一次请求仍用真实 `peek_hashes` 查找，无法命中刚刚写入的派生记录，会重复执行本地二分并重复生成 task。

修改方案：统一计算 `effective_upstream_hashes = upstream_hashes or peek_hashes`（仅在无错误且所有探针均命中缓存时），key、dependencies、来源聚合全部使用同一组 hash；补“预置 API cache、空 derived cache、连续两次请求”的回归测试。

#### F71：异步请求仍有跨功能旧响应回写窗口（medium）

已有 generation guard 覆盖主要等时圈 `setOrigin`、规划结果和执行重排，但仍有三处可见窗口：

- `web/src/stores/plan.ts:326-361` 在 generation 校验前先写入 `travelTimes`，且等待矩阵后才读取当前 `tasks` 组装 `createPlan` 请求；编辑/复位期间旧矩阵可能污染新状态并触发多余 live 请求。
- `web/src/stores/commute.ts:190-307` 重算时没有递增 `evidenceSeq`、清空 `compareTokens`；旧证据/对比等时圈可能回写新路线。
- `web/src/stores/isochrone.ts:45-86` 切换阈值时不递增 `poiSeq`，旧阈值的圈内 POI 结果可能显示在新阈值下。

修改方案：在请求开始冻结输入快照；所有状态写入、错误和 finally 都检查同一 generation；重算/复位同时失效 evidence、compare、POI 子请求；补“请求中编辑/复位/切阈值后旧响应返回”的回归测试。
