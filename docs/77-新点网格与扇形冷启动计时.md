# 重庆湖广会馆：新网格与原扇形计时

2026-10-16，用户要求选一个新点比较两种算法的真实时间。百度地点检索得到中心BD09 `(106.59334,29.563911)`；距最近的历史实验中心约1812米，没有复用既有中心。

## 条件

- 同一中心，步行阈值900秒，每种算法最多316对。
- 原算法为`m3-adaptive-batched-v1`：16向起步、自适应加密，原括界自动上扩至1800米，50米二分容差；不是只测16条路线。
- 新算法为`grid-frontier-barrier-v3`：100米格、半径1000米圆盘、含贯穿轴线和内部屏障追踪。
- 每种算法独立新建空缓存和独立账本，全部实测，无历史数据回填。两种算法共用同一发送节奏配置和相同百度服务限流参数，各批≤50对串行。两次之间冷却10秒，不计入任一耗时。
- 顺序为原扇形、新网格；只测一轮，未做重复压测。

## 如何解读

这轮新网格实际少用77.114秒，但原扇形前10次API调用每次约10.2秒，之后接口恢复较快，新网格在较快响应阶段执行。因此不能把全部时间差归因于算法，也不能用一次测试得出普遍速度倍数。

新网格请求从20次减到10次、查询从286对减到265对，是本轮可核对的算法工作量差异。其半径限制也更小：新网格1公里，原扇形1.8公里括界，最终扇形最大半径约1034米；没有完整参考网格，不能声称新算法同范围同精度更快。

首次快照时间是算法已具备可发布数据的时间；不包括地点搜索、底图加载、浏览器轮询。总时间包含真实请求、发送节奏、服务内部限流及算法快照/几何处理；未计绘图脚本和两算法间10秒冷却。`apiSeconds`字段是服务调用总时长，含其内部等待；上游实际耗时应读账本`latencyMs`，不能把两者混用。
