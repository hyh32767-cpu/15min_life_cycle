# 新AK与串行策略视频主圈重测

2026-10-16用户要求使用新策略和.env内新密钥重测视频中的等时圈，比较耗时。用户明确确认新值是服务端AK，只是误填在BAIDU_MAP_SK名下；本轮只将该变量名改为BAIDU_MAP_AK，未输出密钥，也未将其同步到服务器。测试进程不使用签名SK。

## 同一任务与测试策略

与视频一致：王府井BD09中心116.417939,39.915062，900秒，16个初始方向，自适应加密，loM=200/hiM=1400/initialM=800/tolM=25/maxPairs=320，先返回预估再等待真实终态；不测5/10分钟层或设施。

使用正式IsochroneService、BaiduService与BaiduAdapter，在单独测试进程中注入以下节奏，不修改生产代码中的默认策略：

- 串行在途请求1，每批最多50对，保留真实有向步行矩阵、缓存、账本和错误处理。
- 以已测10/1.8、20/4.1、30/6、40/7.2、50/9秒档位为控制点，对中间批量线性插值并向上取整到0.1秒；下一批发出时刻至少为上一批发出时刻加上一批对应间隔，已经过去的网络耗时不重复等待。
- 401继续走原15秒等接口冷却；测试节奏在收到401时放慢25%，不自动加速恢复。
- 新建独立空API/派生缓存，避免原生活圈或OD缓存令本次速度失真。正式原缓存未清空。
- 本地直连百度、正常TLS验证。新AK不是旧账号权益的自动延续，密钥及路由响应均可能与原视频不同。

工具：`tools/demo/benchmark_video_isochrone.py`，必须显式--run-live。发送节奏用假时钟核对上一批成本、剩余等待及控制点，检查不发真实请求。

## 等待与限制

本次前两批48对/16对分别响应10.240秒和10.251秒，均成功；没有将慢成功响应当作网络超时。后续正常响应多数约0.2秒。第一次完整边界先于加密结束，不作为整圈完成时间。

两个401发生在收尾的2对和1对小批次，仍引入两次约15秒冷却。说明只按路线对数插值发送间隔，未充分解决小批次连续请求的限制；不能仅凭该现象认定确切HTTP QPS或新账号配额。串行本身不足以消除限流，也不能把旧AK下档位直接当作新AK稳定权益。

同样参数下本次取得更多有效探针（299而非274），计算工作并非完全相同；新AK、路由数据差异和观察精度也限制了对纯调度效果的归因。

仅重测这一次，不继续用追加整圈掩盖失败。23条成功原始批次保留到本地api/var/cache.db，保持原fetchedAt/expiresAt，不延长TTL；失败缓存不导入。新策略仅在测试进程中使用，原运行后端与腾讯云配置未切换，也未部署新AK。
