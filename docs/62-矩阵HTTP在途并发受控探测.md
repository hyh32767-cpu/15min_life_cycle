# 矩阵HTTP在途并发受控探测

2026-10-16用户要求测试百度并发，并询问不触发限流是否就不需要15秒等待。

## 实验设计

从腾讯云服务器直连现有百度步行矩阵接口，使用现有服务端凭据。探测进程单独安排发送节奏，调用正式BaiduAdapter，启用产品凭据上下文，因此每次仅一次尝试，没有适配器隐式重试。每次调用记录到产品账本`concurrency-probe-20261016`阶段，有效响应写入现有API缓存；没有写研究账本、输出密钥或修改生产配置。

每组固定16对OD，组起始间隔6.2秒。1/2/4/8个并行请求对应每请求16/8/4/2对，避免把提高HTTP并发与提高每组路线数混淆。线程屏障同时放行，每个请求记录从调用适配器前到返回后的单调时间，计算客户端在途峰值；这是客户端调用重叠证据，不是百度内部同时处理线程数的观测。

计划各档两组，预算最多128对；先排除有效缓存中的探针，遇到任何业务/网络/结果完整性错误即停止后续组。实验不经过服务层本地令牌桶/路线窗口/冷却，以免测到本地排队而非上游响应；受单独的预算、组间隔及停止条件约束。未改变正在服务的限流器或取消线上保护。探测进程与网站共享百度账号，不能排除外部账号流量影响。

客户端峰值在途数各为1/2/4/8，证实本轮请求存在真实调用重叠。实际共22次HTTP尝试、112对成本、108对有效、2次401；网络响应耗时累计2.494秒（并行响应不能简单相加为墙钟）。整个实验37.355秒，主要包括预设的组间间隔，不能当作112对实际计算用时。

8并发出现401后未重试、未执行第二组或继续探测更高档，也未再跑整圈。不能把短测通过的4并发称为长期稳定上限；失败也不足以独立证明某项精确QPS/在途/路线额度，仍可能涉及突发窗口或累计用量。

## 对15秒等待的解释

生产服务的15/30/60秒是收到百度业务401后由本项目设置的接口冷却，不是每次矩阵查询必须等待15秒。若本次没有401、同接口也没有其他请求留下的冷却，就不会触发该冷却路径；仍可能等待HTTP令牌、OD路线数窗口和全局请求槽，或遇到网络慢响应。

本轮16对总量下的4请求短测结果不能推广为“4请求×每请求50对”。优化应同时控制请求发送节奏、OD路线成本与本地排队超时；本次未修改这些实现。
